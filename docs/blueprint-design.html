Design Review · Frontend → Scheduler → Solver → Inventory DB

藍圖調度設計

多 cluster 規劃期聯合求解，執行期照藍圖驗證式靜態置入；支援「部分藍圖、部分動態」混合情境。互動模擬器為示意（簡化貪婪引擎），非真實 CP-SAT 求解。

架構總覽 互動模擬器 混合模式 E2E DB Schema 風險與 FAQ

1 · 架構總覽

核心決策：blueprint（藍圖）是 scheduler side 的概念——它有狀態（世代、active/superseded、與調度單的關聯），所以歸 inventory DB 管；solver 維持無狀態純函數，零改動。規劃、逐批執行、動態插單、重規劃，全部只用 solver 既有的 /v1/placement/solve 一個端點完成。

為什麼「照藍圖靜態置入」是安全的：前綴安全性

C2（容量）、C3（anti-affinity）、C4（max-per-BM）、C6（獨占）全部是「Σ ≤ cap」型約束——聯合可行解的任何子集必然可行。所以只要現實與藍圖一致，照藍圖分批置入，任何建置順序的任何中間狀態都自動可行。這與 ADR-013「聯合可行 ≠ 逐批可行」不矛盾：那個警告針對「每批重新求解」的貪婪路徑；藍圖消除了執行期的選擇，也就消除了路徑依賴。
唯一例外是 C5（failover N-1）：backup 建成之前保護本來就不成立。這是建置期暫態（今日逐批建置亦然），非新風險，但排程順序宜讓 backup 早建。

為什麼只用 /solve

端點結論理由
/solve採用契約最小、語意清楚。規劃、驗證、動態插單、重規劃都只是 vms 裡三種身分的不同組合，Go 只需對接一個端點。
/split-and-solve未來選項欄位是 /solve 的超集加必填 requirements；requirements=[] 時 splitter 產生 0 台、交給同一個求解器，結果相同。現階段一律是明確 VM，用不到依資源用量切分。
/rollout對照工具逐批貪婪模擬，每一步只看到自己這批。拿來重規劃會把藍圖要消滅的路徑依賴請回來。留著回答「不用藍圖、照順序逐批建會不會卡住」。
每次執行期請求都帶整份 active 藍圖，不只本批：已建帶 pinned_to，所有未建 VM 鎖在藍圖 BM，規則原樣傳入，scheduler 只執行本批。原因是 auto C3 的上限依請求中的群組 VM 數計算，只送一部分時上限變小，藍圖裡合法的位置會被誤判 INFEASIBLE；failover 規則的 selector 對不到 VM 則直接 INPUT_ERROR。用 4 cluster／76 VM 範例實測，整份藍圖協議連「同一 cluster 分兩批建」在內的五批全部 OPTIMAL、每次約 0.02 秒。

執行期請求裡的三種 VM 身分

身分表達方式語意
已建事實pinned_to: "bm-x"過去的事實。used_capacity 含其消耗，solver 內部正規化；C3/C4/C5 grandfathered（凍結不惡化）。
藍圖鎖定candidate_baremetals: ["bm-x"]對未來的約束：這台新 VM 必須放藍圖指定的 BM。驗證通過 = 無 drift。
動態自由candidate_baremetals: [...]（池內全部）混合模式的動態插單：solver 現場決定位置。

三種身分可以並存於同一次 solve——這就是「部分藍圖、部分動態」不需要任何 solver 新機制的原因。

    3 · 混合模式 E2E 配套：部分藍圖、部分動態

    真實環境不會只有藍圖流量——藍圖執行到一半，動態的加機需求就會進來。設計上把「計畫外」拆成兩類，配套完全不同：

    受管動態插單野 drift
    定義走 scheduler 的計畫外請求（臨時加 VM）繞過 scheduler 的消耗（人工佔機、BM 故障、帳外 VM）
    處理與藍圖幽靈協同求解（見下），不觸發重規劃下一批驗證 INFEASIBLE 才被發現 → 觸發重規劃
    DB 痕跡schedule_request.mode=dynamic；schedule_placement.blueprint_placement_id = NULL無調度單——事後由 used_capacity 與帳面差額對帳

    藍圖幽靈預留：動態單如何不弄壞藍圖

    動態插單時，scheduler 把「藍圖中尚未建置的 VM」以鎖定 candidates（幽靈）一起放進同一次 solve：

    {
  "vms": [
    {"id":"dyn-worker-1","cluster_id":"adhoc","demand":{...},
     "candidate_baremetals":["bm-1","...","bm-9"]},      // 動態：自由
    {"id":"vm-b-w2","cluster_id":"cluster-b","demand":{...},
     "candidate_baremetals":["bm-5"]},                    // 幽靈：藍圖鎖定
    {"id":"vm-a-m1","pinned_to":"bm-1", ...}              // 已建：事實
  ],
  "baremetals": [ ...真實 used_capacity... ]
}

    solver 只會把 dyn-worker-1 放在不侵蝕藍圖已規劃容量的位置；放不下就 INFEASIBLE（＝動態單被拒，藍圖不受影響）。幽靈的 assignments 回來後 scheduler 直接忽略——它自己知道哪些 id 是幽靈。solver 契約零改動。

    政策點（討論時要定案）：預留保護 vs 先到先贏

    預留保護（推薦，模擬器開關「開」）先到先贏（開關「關」）
    做法動態單與藍圖幽靈協同求解動態單只看當下剩餘容量
    優點藍圖穩定、不觸發重規劃；容量衝突在動態單當下被拒，訊號即時scheduler 實作最簡單；動態單成功率高
    代價動態單可能被拒（需要拒單／排隊的產品流程）藍圖容量被蠶食 → 逐批驗證失敗 → 藍圖頻繁 churn
    適用藍圖池（bm_group 策略 = blueprint / mixed）純動態池（策略 = dynamic）

    建議以 bm_group 為粒度設策略：blueprint-only（拒收動態單）、mixed（預留保護協同求解）、dynamic-only（無藍圖，維持今日行為）。用模擬器把開關關掉，可以親眼看到先到先贏如何把下一批逼成 INFEASIBLE。

    4 · Inventory DB Schema

    設計判斷：schedule_placement 是事實、藍圖是意圖，分表。同一個 VM 會出現在多個世代的藍圖（意圖）裡，但事實永遠只有一筆；混表會讓最熱的「查實際佈局」查詢永遠要濾旗標。分表後 plan-vs-actual 的 drift 報表就是一個乾淨的 join。

    erDiagram
    bm_group ||--o{ bm : contains
    bm_group ||--o{ blueprint : "planned for"
    blueprint ||--o{ blueprint_placement : has
    blueprint |o--o| blueprint : "parent (gen chain)"
    vm ||--o{ blueprint_placement : "planned as"
    bm ||--o{ blueprint_placement : "planned on"
    blueprint ||--o{ schedule_request : "executed by"
    schedule_request ||--o{ schedule_placement : records
    blueprint_placement |o--o{ schedule_placement : "fulfilled by"
    vm ||--o| schedule_placement : "placed as"
    bm ||--o{ schedule_placement : hosts

    新表

    表欄位重點不變量／備註
    blueprintblueprint_id PK、bm_group_id FK、generation + parent_blueprint_id（世代鏈）、status（active/superseded/completed/cancelled）、config_fingerprint、bm_snapshot_fingerprint、request/response JSON 原文歸檔一個 bm_group 同時僅一份 active（partial unique index）。指紋 = drift 快路徑；驗證 solve = 慢路徑兜底。
    blueprint_placementblueprint_id/vm_id/bm_id FK、cluster_id（哪一批）、pinned（重規劃帶入的事實 vs 本代新規劃）、status（planned/placed/superseded）Unique(blueprint_id, vm_id)。pinned 對應 solver 回應旗標，使每代藍圖自我完整。

    既有表加欄位

    表新欄位用途
    schedule_requestnullable blueprint_id FK、批次標識、mode（blueprint/dynamic/mixed）NULL = 傳統 ad-hoc，舊流程不受影響。mode 讓混合池的行為可稽核。
    schedule_placementnullable blueprint_placement_id FK「事實兌現了哪筆計畫」。跨世代後靠 vm_id join 分不清照哪一代放的；明確 FK 才能做 VM 粒度的 plan-vs-actual drift 報表（現有 reconcile 只到容量格粒度）。動態單此欄為 NULL——天然區分計畫內外。
    vmstatus（planned/building/active）※若尚無生命週期欄規劃期即備好 id/name，VM 列在建置前就存在。
    bm_group（可選）policy（blueprint/mixed/dynamic）混合模式的池級策略。bm 不動。

    先不建 blueprint_step 表：step 級狀態可由調度單 + 明細推導；等需要掛獨立 metadata（預計時程、負責人）再升級，避免過早正規化。

    5 · 風險與 FAQ

    Q1 為什麼 solver 完全不用改？

    三個需求各自被既有原語接住：規劃 = 一次普通 /solve（多 cluster 本來就支援，auto-rule 以 (cluster_id, ip_type, node_role) 分組、各 cluster 獨立 spread）；執行 = 「事實 vs 約束」二分（pinned_to vs 單元素 candidate_baremetals，ADR-012）；重規劃 = 同一個 /solve 帶 pins + grandfathering。藍圖唯一的新東西是「狀態」，而狀態歸 DB，不歸純函數。

    Q2 動態插單會不會弄壞藍圖？

    受管的不會：幽靈協同求解讓動態 VM 只落在不侵蝕藍圖容量的位置，放不下就拒單，藍圖不動。會弄壞藍圖的是野 drift（繞過 scheduler 的消耗），它由逐批驗證兜底發現，觸發重規劃。

    Q3 重規劃會不會把已建的 cluster 逼成 INFEASIBLE？

    不會。已建 VM 以 pinned_to 帶入，C3/C4/C5 caps 被 grandfathered（max(cap, 既有數量)）——既有偏斜凍結、不惡化、永不 INFEASIBLE。代價：最佳性降為「給定凍結前綴下的最優」；若前綴嚴重卡死（占走關鍵 AG），唯一出路是 rebalance（unpin + minimize moves），那是獨立的未來模式，不是重規劃的副作用。

    Q3b 重規劃會不會把整份藍圖洗掉？

    會，如果直接放開所有未建 VM。solver 沒有「維持原位置」的目標項，會挑另一個等價的最優解。所以重規劃分兩層：先局部，只放開 diagnostics 點名沒地方放的 VM，其餘未建 VM 仍鎖在藍圖；失敗才全面。實測同一個 drift，局部重規劃移動 4 台，全面重規劃移動 57 台未建 VM 中的 51 台。

    Q4 drift 怎麼分類處理？

    drift 類型偵測訊號處理
    BM 消失／縮容驗證批 INFEASIBLE 或 INPUT_ERROR（pinned 主機不在清單、used > total）重規劃剩餘 cluster
    野 VM 佔用used_capacity 上升被驗證批看見；擠得下照常、擠不下 INFEASIBLE擠不下才重規劃
    需求改版主動觸發（人為決定）重規劃（小幅加 VM 可走 add-node）
    config 漂移config_fingerprint 不一致拒絕執行，重新規劃

    Q5 有沒有已知的坑？

    有一個：solver 裸 solve 路徑對規則裡未知的 vm_ids 是無聲丟棄——打錯 id 會讓 C6 成員集變空、獨占保護蒸發，仍回 OPTIMAL。scheduler 的合併程式是第一線暴露面：短期在合併後自查「規則 id ⊆ VM 清單」並讀回 solver advisory；中期在 solver 的 pure-solve 路徑補 INPUT_ERROR（獨立 follow-up）。

    Q6 什麼訊號出現時要重新審視這個設計？

    drift 率高到藍圖頻繁重規劃時，藍圖失去意義——屆時縮短規劃視窗（一次規劃更少 cluster），或該池退回逐批 rollout。
