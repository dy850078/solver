# ADR-NNN: <一句話標題:改了什麼、為了什麼>

- **日期**: YYYY-MM-DD
- **作者**: <模型名稱或人名>
- **相關 PR / commit**: <連結或 hash>
- **影響範圍**: <touched files>

> 寫作對象:一位正在學習 CP-SAT 與排程系統設計的工程師。
> 寫作口吻:資深工程師帶 code review——不只說「做了什麼」,要說「為什麼、
> 還考慮過什麼、你應該從中學到什麼」。全文使用繁體中文,程式碼與術語保留英文。

## 1. 背景與問題

為什麼需要動這裡?觸發這次改動的需求或缺陷是什麼?
如果讀者沒有上下文,讀完這段要能理解問題本身。

## 2. 考慮過的方案

至少列出兩個方案(含最終採用的那個)。每個方案說明:
- 做法概述
- 優點 / 缺點
- **被排除的原因**(最重要——這是判斷力所在)

## 3. 最終決策

一段話講清楚採用了什麼、核心理由是什麼。

## 4. 實作走讀

像帶新人看 diff 一樣,挑 2–4 個關鍵位置(用 `file.py:line` 標註),解釋:
- 這段程式碼在做什麼(數學意義,不只是字面意義)
- 為什麼寫在這個位置(對應 solver.py 的 Step A–D 哪一階段)
- 有什麼不明顯的細節(邊界條件、CP-SAT 的特性、效能考量)

## 5. 取捨與風險

這個決策犧牲了什麼?什麼情況下它會出問題?未來什麼訊號出現時應該重新審視?

## 6. 你應該帶走的知識

最多三點,每點一兩句。可以是:一個 CP-SAT 建模技巧、一個系統設計原則、
一個這個領域特有的陷阱。這是整份 ADR 的學習重點摘要。

## 7. 驗證方式

哪些測試證明它是對的?(`tests/test_*.py::test_name`)
用哪個 example 可以親手驗證?(`make cli INPUT=examples/...`)
